# 03 移动版可行性分析

目标回顾：把 `dsh` 做成移动应用，**别人直接下载就能用、功能保持不变、开源**，并在 GitHub 建独立开源仓库。本文给出路线对比、结论与分阶段计划。事实依据见 `01-project-analysis.md`（编号事实记为 F1–F7）。

## 1. 候选路线

### A. 远端客户端（瘦客户端壳）

App 复用现有 React Web 前端（F1/F3），连接用户自己运行的 `dsh web` 主机（电脑、NAS、云主机）。执行全部留在主机侧，模型调用本来就是远端 HTTPS（F4）。

- **A1 服务器渲染模式**：WebView 直接加载主机地址（如 Capacitor 的 `server.url`）。前端静态资源由主机伺服，壳里不打资产。前后端版本永远一致，客户端零改动。
- **A2 内置资产模式**：前端打进 App，API 基地址做成可配置（客户端唯一的同源假设集中在 `resolveBase()`，F2）。可离线打开外壳，但要处理跨域、WS 基地址、前后端版本匹配。

### B. 端上移植（手机上跑完整 harness）

把 Node.js 与整个插件树搬进手机。

- **Android**：技术上部分可行（Android 是 Linux 用户态；Termux 今天就能手动跑 Node）。但要产品化：捆绑 Node 运行时、为 Android ARM 预编译 `node-pty`/`koffi`、处理 Landlock 内核对版本的依赖（`native/landlock-run`）、应对 Google Play 对下载执行代码的政策。工程量巨大。
- **iOS**：不可行。系统禁止 `fork/exec` 任意子进程，`node-pty`、Bash 工具、LSP、MCP 等主机侧能力全军覆没（F3），违反"功能保持不变"的硬约束。

### C. 纯 PWA

补 service worker + 移动 UI，用"添加到主屏幕"安装。上游已有 manifest（F6）。不经过商店，但 iOS 对 PWA 限制多（推送、后台、安装引导差），且不算"下载一个 App"。适合作副产品，不作主交付。

### D. 托管云 + App

我们运营托管主机，用户登录即用。引入持续成本与信任问题（用户代码/密钥在我们服务器上），与"纯开源分发"的定位冲突。可作远期可选项，不作主线。

## 2. 对比结论

| 维度 | A 远端客户端 | B 端上移植 | C 纯 PWA | D 托管云 |
|---|---|---|---|---|
| 功能保持不变 | ✅ 执行全在主机 | ❌ iOS 不可能 | ✅ | ✅ |
| 直接下载即用 | ✅（APK/商店；需配主机） | ⚠️ 仅 Android 理论上 | ⚠️ 安装体验弱 | ✅ 但需注册账号 |
| 工程量 | 中（壳+认证+移动 UI） | 极大且无止境 | 小 | 大（含运营） |
| 政策/审核风险 | 低 | 高（Play 政策、iOS 禁止） | 无 | 中 |
| 开源契合度 | 高 | 中 | 高 | 低 |

**结论：A 是唯一同时满足三条硬约束的路线，可行。** B 在 iOS 上的功能缺失是硬伤，否决；C 作为零成本副产品保留；D 记入远期候选。

## 3. A 路线的三个缺口（均不触碰 agent 核心）

1. **认证与加密（阻断项）**：上游主机没有任何认证（F5），端口一旦可被手机访问，等于把主机 shell 暴露给网络。必须在移动版落地前解决：
   - 近期：反向代理方案（Caddy/nginx 终结 TLS + token 校验）或组网方案（Tailscale/WireGuard），写进用户文档；
   - 正解：向上游提交可选 token 认证（webserver/apiproxy 配置项 + `/api` 与 WS 握手校验）。这对上游桌面用户开放 LAN 也有价值，被接受的概率高；若上游暂不接受，移动仓库以 cordis patch/bundle 形式外挂一个认证代理插件（F7 允许不改核心）。
2. **API 基地址与配对 UX**：A1 模式无需改客户端；但服务器地址输入、二维码配对（主机端打印含地址+token 的二维码）、自签名证书处理、断线重连，都是壳层工作。
3. **移动 UI 适配**：现有界面无移动断点（F6）。平板上可接受，手机上需要响应式改造。建议作为上游 PR 推进（桌面窄窗口同样受益），分阶段：先可用的会话/审批路径，再全量。

## 4. 壳技术选型（A 路线内）

| 选项 | 评估 |
|---|---|
| **Capacitor（推荐）** | MIT 许可；iOS/Android 成熟；直接复用 Web 资产与 `server.url` 模式；原生桥可补安全存储 token、后台保活、推送。 |
| Tauri Mobile | 包体更小、Rust 底座，但移动端支持较新、生态与踩坑成本高，对"复用现有 Vite 构建"没有增量收益。 |
| React Native 重写 | 现有约 40 个 `ui-*` React DOM 包要全部重写，工程量最大且持续跟随上游改动，否决。 |
| 原生 WebView 手写 | 可控但两边都要维护样板（生命周期、键盘、安全区、文件下载），Capacitor 已解决，无必要。 |

## 5. 分发与开源仓库规划

- **仓库**：GitHub 新建 `dsh-mobile`（暂定名），MIT 许可。内容：Capacitor 壳工程、配对/认证相关插件或 patch、文档（本目录迁移）、CI。
- **Android**：GitHub Actions（ubuntu）构建 APK/AAB → GitHub Releases 直接下载，同时上传国内可访问镜像；后续可上 F-Droid/各厂商商店。
- **iOS**：GitHub Actions（macos runner）构建 → TestFlight / App Store。WebView 壳类应用可过审（属远程开发工具的正式客户端）；无法提供"直接下载 IPA"的合法大众路径，TestFlight 是最低摩擦方案。
- **版本策略**：上游处于开发者预览、声明有破坏性变更，壳与文档固定对接上游的 npm 发布版本（当前 `0.1.0-rc.5`），跟随 release 升级，不追 git main。

## 6. 分阶段路线图

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 可行性 | 本文档与 ADR（已完成） | 结论评审通过 |
| 1 PoC（局域网） | Capacitor 壳 + `server.url`；主机 `host: 0.0.0.0` 同 Wi-Fi 直连；验证会话、工具审批、终端、附件全链路 | Android APK 在 Releases 可下载，真机跑通核心路径 |
| 2 安全远程访问 | token 认证（上游 PR 或外挂代理插件）+ TLS + 二维码配对 | 公网暴露的主机无 token 不可驱动；扫码即连 |
| 3 移动体验 | 响应式 UI（上游 PR）、A2 内置资产离线壳、断线重连、iOS TestFlight | 手机屏核心路径可用；双端分发 |
| 4 远期候选 | 推送通知、托管云选项、F-Droid/商店上架 | 视社区反馈排期 |

工作量粗估（1 人）：阶段 1 约 1–2 周；阶段 2 约 2–4 周（上游评审周期是变量）；阶段 3 最大头且随上游 UI 演进持续投入。

## 7. 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 上游认证 PR 不被接受/周期长 | 中 | 外挂 cordis patch 认证代理兜底（F7） |
| 上游破坏性变更（开发者预览） | 高 | 钉 npm release 版本；snapshot 测试随上游升级同步跑 |
| iOS 审核对"远程执行工具"的审查 | 低-中 | 定位为自托管客户端，提供审核说明与演示账号 |
| 手机浏览器/WebView 对 SSE+WS 的兼容性 | 低 | 协议是标准 HTTP/SSE/WS（F1），PoC 阶段真机验证 |
| Google Play 政策（如后续上架） | 低 | APK 直接分发为主渠道，商店为可选 |
| 用户没有可运行的主机 | 中 | 文档提供一键部署（npx/docker）与桌面端"为手机开启"向导；远期托管云兜底 |

## 8. 最终结论

**可行，推荐立即进入阶段 1 PoC。** 架构决定与选型理由固化在 [ADR-0002](decisions/ADR-0002-architecture-remote-client.md)。唯一需要预告的偏差：iOS 无法做到"直接下载安装"，TestFlight/App Store 是合规路径；功能保持不变的含义是"连接自托管主机后功能不变"，App 本身不内置执行引擎。
