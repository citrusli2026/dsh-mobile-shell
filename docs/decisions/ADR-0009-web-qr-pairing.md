# ADR-0009 Web 二维码配对：单次码 fragment、本地生成、用户确认

- 状态：已接受（2026-08-15）
- 依据：[ADR-0006](ADR-0006-pairing-code-and-tls.md)（单次短码）、[ADR-0008](ADR-0008-device-session-and-web-hardening.md)（设备会话与长期凭据边界）

## 背景

Web 模式已经可以安全配对，但首次使用仍要从电脑终端抄局域网地址和 6 位码；多网卡、域名反代和再次签码还要手工拼 URL/curl。目标是做到“拿手机扫码、确认一次即可进入”，同时不把主令牌或设备令牌重新放回 URL。

## 决策

1. 配对链接固定为 `http(s)://<代理>/launch#pair=<6位码>`。fragment 不随 HTTP 请求发送；启动页读取后立即用 `history.replaceState` 清除，只把码放入输入框。
2. 启动页不自动兑换。用户必须点一次“确认配对并连接”，避免操作系统链接预览、安全扫描器或自动化抓取误消耗单次码。
3. 二维码只编码代理 Origin 和 ADR-0006 的 10 分钟、单次码；不编码主令牌、设备令牌或任何可长期重放的凭据。
4. 代理用本地 vendored 的 Project Nayuki QR encoder 生成终端 QR，不调用在线二维码服务。源码固定在 v1.8.0，保留完整 MIT 许可证与来源 commit。
5. `0.0.0.0` 监听时自动枚举非 internal IPv4 生成候选链接；域名、TLS 终止、多网卡/Tailscale 场景用 `DSH_PUBLIC_URL` 明确指定公开 Origin。错误配置启动即失败。
6. 交互终端输入 `n` 回车可签发新码并打印新链接/QR；后台仍用主令牌保护的 `POST /pair/new`，响应增加 `pairingUrls`。`DSH_PAIR_QR=off` 只关闭 ANSI QR，不关闭码或链接。

## 后果

- 首次使用从“抄地址 + 抄码”缩短为“扫码 + 一次确认”，且长期凭据边界不变。
- URL fragment 可能被浏览器历史短暂持有，因此启动页必须在任何网络请求前清除；自动化对此做稳定断言。
- 自动网卡发现无法判断用户真正想用的 VPN/域名，故只作为局域网默认；生产反代应显式设置 `DSH_PUBLIC_URL`。
- 被否决方案：
  - **在线 QR API**：会向第三方泄漏内网地址和短码，且破坏离线部署，否决。
  - **二维码编码主令牌/设备令牌**：把短期配对重新退化为长期 bearer 分发，否决。
  - **查询参数 `?pair=`**：会进入 HTTP 日志和中间层，fragment 更合适。
  - **扫码后自动兑换**：可能被预览器抢先消耗单次码，否决。

## 取代关系

扩展 ADR-0006 的配对 UX 与 ADR-0007 的 Web 启动页；不改变 ADR-0008 的设备会话和长期凭据安全边界。
