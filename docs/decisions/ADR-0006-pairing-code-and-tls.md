# ADR-0006 阶段 2：配对码兑换令牌 + 可选 TLS（用户供证），不做自签自动信任

- 状态：已接受（2026-08-14）
- 依据：[ADR-0004](ADR-0004-token-proxy.md) 的共享密钥局限；阶段 1 PoC 实录（[05](../05-phase1-poc.md)）

## 背景

阶段 1 的配对方式是"手打主机地址 + 手打主令牌"：易输错、主令牌多次出现在输入法/剪贴板里，且明文在局域网可被嗅探。ADR-0004 给阶段 2 留了两件事：TLS 终结、更强的配对。

TLS 的现实约束（本轮核实）：WKWebView/Android WebView 都不会信任自签证书；让手机信任私有 CA 要装描述文件/用户证书，对"下载即用"是不可接受的摩擦。手机端可信 TLS 的正路是**公网 CA 签名的域名证书**（Let's Encrypt、Caddy、用户的反向代理），那只可能由部署方提供，App 无从自动。

二维码摄像头的现实约束：模拟器摄像头是假数据源，双端都无法真实验证扫码；引入 ML Kit 等原生扫码依赖会扩大包体与构建面，收益现阶段为零。

## 决策

1. **配对码兑换令牌**（对标 KDE Connect 短码模型）：
   - 代理新增 `POST /pair/new`（主令牌鉴权）：签发一个 6 位数字配对码，单次使用、10 分钟过期、按源 IP 限速（10 次/分钟）。启动时自动打印一个初始配对码。
   - 代理新增 `POST /pair`（公开、CORS `*`、正确处理 OPTIONS 预检）：凭码换真令牌；错误/过期 403，超限 429。常量时间比较。
   - App 启动页新增"配对码连接"模式：输入主机地址 + 6 位码 → 兑换 → 记忆 → 进入。主令牌全程不出现在手机上。
2. **TLS 做成可选项，用户供证**：`DSH_TLS_CERT`/`DSH_TLS_KEY` 同时配置时代理以 HTTPS 监听（WS 同端口升级为 WSS；Cookie 自动加 `Secure`）。不生成自签证书、不做 App 端证书信任绕过——文档明确：公网部署走域名证书（Caddy/Let's Encrypt 或自有反代），可信局域网继续用明文 + 令牌。
3. 双端工程的明文开关（`usesCleartextTraffic`/`NSAllowsArbitraryLoads`）维持现状：配对码模式默认仍面对局域网明文场景；公网 TLS 部署的用户另见文档指引，后续阶段再收窄。

## 后果

- 配对安全边界：6 位码 + 单用 + 短 TTL + 限速，局域网威胁模型下充分；配对码本身经明文可见，但截获者须在 10 分钟内、抢在合法用户前、且每码只有一次机会——窗口足够小。公网部署必须 TLS（文档强制声明）。
- 被否决方案：
  - **自签证书 + App 信任**：双端 WebView 均不提供可行的程序化信任路径，安装 CA 的摩擦违背"下载即用"，否决。
  - **摄像头扫码（ML Kit）**：模拟器不可验证、原生依赖膨胀；配对链接格式预留为阶段 3 再加（届时真机验证）。
  - **HMAC 逐请求签名替代 Cookie**：把 PoC 工具做成分布式协议，收益不成比例，否决。
- 遗留：多用户/吊销仍无；如上游合入认证 PR（ADR-0002 正解路径），配对码可映射到上游会话。

## 取代关系

细化 ADR-0002 阶段 2 与 ADR-0004 遗留项的实施方案；不改变其架构判断。
